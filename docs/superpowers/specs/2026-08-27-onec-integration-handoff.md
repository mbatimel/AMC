# Интеграция AMC ↔ 1С: полный handoff 1С-разработчику

Сводный документ — всё, что нужно 1С-стороне для обеих интеграций (каталог и заказы). Собран
из двух источников:
- `back/integrations/README.md` — разведка канала для синка каталога (актуально на 2026-08-25).
- `docs/superpowers/specs/2026-08-26-onec-orders-integration-1c-contract.md` — контракт по заказам (актуально на 2026-08-26).

Эти два файла остаются источником деталей/рационале; этот документ — то, что можно отдать
1С-разработчику одним куском.

Статус обеих частей: **черновик**, не сверен с реальным сервером 1С (`PVISERVER`, база `UT`,
УТ 10.3). Часть А ждёт публикации OData на сервере (пока не сделано — см. ниже). Часть Б ждёт
реализации кастомной HTTP-ручки на стороне 1С.

---

## Часть А — каталог (номенклатура, цены, остатки)

Раз в сутки наш воркер (`onec-sync`) тянет из 1С номенклатуру, цены и остатки и обновляет ими
нашу БД товаров.

### Что нужно сделать в 1С (инфраструктурно, не программирование)

1. Установить роль **IIS** на сервере `PVISERVER`, если ещё не установлена (Диспетчер серверов
   → Добавить роли → Веб-сервер IIS) — без веб-сервера ни OData, ни HTTP-сервисы не
   опубликовать. На момент разведки веб-сервер не стоял.
2. В Конфигураторе базы **`UT`**: Администрирование → Публикация на веб-сервере → включить
   галку **"Стандартный интерфейс OData"**. Платформа `8.3.27` это поддерживает (нужна 8.3.5+).
3. Завести отдельного технического пользователя 1С с правами **только на чтение** нужных
   справочников/регистров (см. список ниже) — не полный доступ.
4. Сообщить нам: URL для подключения (снаружи — по интернету с ограничением по IP, или через
   VPN, как у вас принято), логин/пароль техпользователя.

Если OData по какой-то причине не подходит — запасной вариант: кастомный HTTP-сервис с одним
методом, отдающим JSON (номенклатура+цены+остатки), либо регламентная выгрузка в CSV/JSON в
шаренную папку. Наш воркер сегодня рассчитан на OData; переход на другой вариант потребует
правок на нашей стороне — сообщите, если OData не вариант, обсудим отдельно.

### Что именно нужно отдавать

| Сущность | Объект 1С (предположительно) | Нужные поля |
|---|---|---|
| Категории товаров | `Catalog.НоменклатурныеГруппы` | GUID, родитель (иерархия), наименование |
| Склады | `Catalog.Склады` | GUID, наименование |
| Товары | `Catalog.Номенклатура` | GUID, артикул/код, наименование, категория |
| Цены | `InformationRegister.ЦеныНоменклатуры` | товар, тип цены, цена |
| Остатки | `AccumulationRegister.ТоварыНаСкладах` | товар, склад, количество |

Стандартные имена OData entity set'ов, которые мы предполагаем (сверить с реальным сервером
после публикации — могут отличаться):

```
Catalog_НоменклатурныеГруппы   (Ref_Key, Parent_Key, Description)
Catalog_Склады                 (Ref_Key, Description)
Catalog_Номенклатура            (Ref_Key, Code, Description, НоменклатурнаяГруппа_Key)
InformationRegister_ЦеныНоменклатуры  (Номенклатура_Key, ТипЦен_Key, Цена)
AccumulationRegister_ТоварыНаСкладахBalance  (Номенклатура_Key, Склад_Key, КоличествоBalance)
```

**Вопрос вам:** какой именно тип цены из `ТипыЦенНоменклатуры` брать (розничная/оптовая/
клиентская)?

### Что пока не нужно (вне первой очереди), но пригодится позже

Бренд, ГОСТ, материал, размер, изображения, единицы измерения, ценовые группы клиентов — в
манифесте конфигурации не нашли отдельных справочников под это. Вероятно доп.реквизиты/
доп.сведения номенклатуры, либо не ведётся в 1С вовсе. **Вопрос вам:** где физически хранится
каждое из этого (если хранится)?

Также: **есть ли у объектов поле даты изменения** — пригодится для инкрементальной
синхронизации (тянуть только изменённое, не всю базу каждый раз). Сейчас синкаем полностью
при каждом прогоне.

## Часть Б — заказы

При оформлении заказа на сайте мы синхронно передаём его в 1С; когда заказ доставлен, 1С
сообщает нам об этом отдельным вызовом. Две ручки, в разные стороны.

### Ручка №1 — приём заказа (реализовать у себя в 1С)

Мы вызываем её синхронно в момент оформления заказа. Если 1С не ответила успехом — заказ у
нас не создаётся вообще, клиент видит ошибку. Таймаут на нашей стороне — 15 секунд, отвечать
нужно быстро.

```
POST /hs/amc-integration/orders
Content-Type: application/json
Authorization: Basic <технический пользователь 1С, read-write>
```

```json
{
  "client_order_id": "b7e6c2b0-1234-4d9a-9a0e-8f1a2b3c4d5e",
  "order_number": "AMC-20260826-00042",
  "counterparty": {
    "onec_guid": "b1a2c3d4-...",
    "inn": "7701234567",
    "name": "ООО Ромашка"
  },
  "delivery": {
    "type": "delivery",
    "address": "г. Москва, ул. Примерная, д. 1",
    "contact_name": "Иван Иванов",
    "phone": "+79991234567",
    "email": "ivan@example.com"
  },
  "comment": "Позвонить перед доставкой",
  "items": [
    {
      "onec_guid": "c1d2e3f4-...",
      "sku": "AMC-00123",
      "name": "Дрель ударная",
      "qty": 2,
      "price": 4500.00,
      "vat_rate": 20
    }
  ]
}
```

**`client_order_id`** — UUID заказа у нас. Это ключ идемпотентности: повторный запрос с тем же
`client_order_id` (например у нас случился сетевой сбой и мы retry-нули) не должен создавать
второй документ — верните тот же `onec_document_guid`/`onec_document_number`, что и в первый
раз.

**`counterparty.onec_guid`** и **`items[].onec_guid`** могут быть пустой строкой — значит, мы
ещё не знаем GUID (новый клиент/товар, которого 1С ещё не видела). В этом случае нужно
смэтчить контрагента по `inn` (или завести нового, если не нашли) и смэтчить товар по `sku`.
Правила матчинга/создания — на ваше усмотрение, только задокументируйте где-нибудь у себя.

Ответ, успех — `200 OK`:
```json
{ "onec_document_guid": "d4e5f6a7-...", "onec_document_number": "УТ-00456" }
```

Ответ, ошибка — любой код кроме `200` (например `400` при некорректных данных, `500` при
внутренней ошибке 1С), тело `{"error": "текст"}` — мы считаем заказ не принятым, откатываем
создание целиком.

### Ручка №2 — статус заказа (вызывать у нас, когда доставлено)

```
POST https://wk.amctechgroup.ru/api/v1/onec/orders/status
Content-Type: application/json
X-Onec-Api-Key: <статический ключ, выдаётся отдельно>
```

```json
{
  "client_order_id": "b7e6c2b0-1234-4d9a-9a0e-8f1a2b3c4d5e",
  "status": "delivered",
  "onec_document_number": "УТ-00456",
  "comment": "Вручено получателю 26.08.2026"
}
```

- **`client_order_id`** — тот же UUID, что вы получили и сохранили в ручке №1 (эхо, не GUID
  документа). Обязательное поле, по нему мы находим заказ.
- **`status`** — в v1 допустимо **только `"delivered"`**. Любое другое значение (`"cancelled"`,
  `"new"`, `"processing"` и т.д.) мы отклоним с `400` — эти статусы 1С не назначает (отмена —
  только у нас, по действию клиента/менеджера). Список расширится позже отдельным
  согласованием.
- **`comment`** — опционально, попадёт в историю статусов заказа как есть.

Ответы:
- `200 OK`, `{"ok": true}` — применено (или уже было применено раньше — повтор с тем же
  статусом безопасен, дублей не создаёт).
- `400` — недопустимый `status` или нет обязательного поля.
- `401` — неверный/отсутствующий `X-Onec-Api-Key`.
- `404` — заказ с таким `client_order_id` не найден.
- `409` — заказ уже отменён у нас (`cancelled`) — терминальный статус, вы не можете перевести
  такой заказ в `delivered`. Повторять не нужно.

Тело ответа при любой ошибке — `{"ok": false, "error": "<код ошибки>"}`, где `error` — наш
внутренний код для логов. Ориентируйтесь на HTTP-статус, а не на текст `error`.

При `5xx`/отсутствии ответа — можно повторить позже, вызов идемпотентен. При
`400`/`401`/`404`/`409` — повторять бессмысленно без изменения запроса.

   передан — вы определяете и документируете у себя.
