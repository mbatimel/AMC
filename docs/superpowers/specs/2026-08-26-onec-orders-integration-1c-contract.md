# Контракт AMC ↔ 1С: заказы

Документ для 1С-разработчика. Две ручки: одну поднимает 1С у себя (AMC её
вызывает при оформлении заказа), другую вызывает 1С (когда заказ доставлен).
Технический фон и решения на стороне AMC — в соседнем файле
`2026-08-26-onec-orders-integration-design.md`, здесь — только сам контракт.

Статус: **черновик**. Пути, имена полей и порт — рабочие предположения по
аналогии с уже согласованным OData-доступом (см.
`back/integrations/README.md`); не сверены с реальным сервером 1С, как и
подключение OData у вчерашнего воркера синхронизации товаров. Значения auth
(логин/пароль/API-ключ) — заглушки, реальные секреты выпускаются отдельно и
не попадают в этот документ.

---

## 1. Ручка №1 — создание заказа (1С поднимает у себя)

AMC вызывает её синхронно в момент оформления заказа клиентом. Если 1С не
ответила успехом — **заказ в AMC не создаётся вообще**, клиент видит ошибку.
Отвечать нужно быстро — таймаут на стороне AMC 15 секунд.

### Запрос

```
POST /hs/amc-integration/orders
Content-Type: application/json
Authorization: Basic <технический пользователь 1С, read-write>
```

```json
{
  "client_order_id": "b7e6c2b0-1234-4d9a-9a0e-8f1a2b3c4d5e",
  "order_number": "AMC-20260826-00042",
  "counterparty": {
    "onec_guid": "b1a2c3d4-...",
    "inn": "7701234567",
    "name": "ООО Ромашка"
  },
  "delivery": {
    "type": "delivery",
    "address": "г. Москва, ул. Примерная, д. 1",
    "contact_name": "Иван Иванов",
    "phone": "+79991234567",
    "email": "ivan@example.com"
  },
  "comment": "Позвонить перед доставкой",
  "items": [
    {
      "onec_guid": "c1d2e3f4-...",
      "sku": "AMC-00123",
      "name": "Дрель ударная",
      "qty": 2,
      "price": 4500.00,
      "vat_rate": 20
    }
  ]
}
```

**`client_order_id`** — UUID заказа в AMC. Это ключ идемпотентности: если 1С
получит запрос с уже обработанным `client_order_id` (повтор из-за сетевого
сбоя на стороне AMC), нужно **не создавать второй документ**, а вернуть тот
же `onec_document_guid`/`onec_document_number`, что и в первый раз.

**`counterparty.onec_guid`** и **`items[].onec_guid`** могут быть пустой
строкой — значит, AMC ещё не знает GUID (новый клиент/товар, которого 1С не
видела ни разу). В этом случае 1С обязана сматчить контрагента по `inn`
(либо завести нового, если не нашла) и матчить товар по `sku` (артикулу).
Правила матчинга/создания — на усмотрение 1С-стороны, только зафиксируйте их
где-то в документации 1С-конфигурации, чтобы можно было сверить при
расхождениях.

### Ответ, успех — `200 OK`

```json
{
  "onec_document_guid": "d4e5f6a7-...",
  "onec_document_number": "УТ-00456"
}
```

### Ответ, ошибка

Любой код, отличный от `200` (например, `400` при некорректных данных
контрагента/товара, `500` при внутренней ошибке 1С) — AMC считает заказ не
принятым, откатывает создание заказа целиком.

```json
{ "error": "текст ошибки для лога" }
```

## 2. Ручка №2 — статус заказа (1С вызывает AMC)

Дёргается 1С каждый раз, когда заказ переходит в статус, о котором должен
узнать AMC. В v1 это **только доставка**.

### Запрос

```
POST https://wk.amctechgroup.ru/api/v1/onec/orders/status
Content-Type: application/json
X-Onec-Api-Key: <статический ключ, выдаётся отдельно>
```

```json
{
  "client_order_id": "b7e6c2b0-1234-4d9a-9a0e-8f1a2b3c4d5e",
  "status": "delivered",
  "onec_document_number": "УТ-00456",
  "comment": "Вручено получателю 26.08.2026"
}
```

**`client_order_id`** — тот же UUID, что 1С получила и сохранила при вызове
ручки №1 (эхо, не GUID документа 1С). Обязательное поле — по нему AMC находит
заказ, обратного поиска по GUID документа нет.

**`status`** — допустимые значения в v1: **только `"delivered"`**. Любое
другое значение (в т.ч. `"cancelled"`, `"new"`, `"processing"`) AMC отклонит
с `400` — эти статусы 1С не назначает (`cancelled` — только клиент/менеджер
на стороне AMC). Список будет расширяться (например под "собран"/"отгружен")
отдельным согласованием — заранее произвольные значения слать не нужно, они
будут просто отклоняться.

**`comment`** — опционально, попадёт в историю статусов заказа как есть.

### Ответ

- `200 OK`, `{"ok": true}` — статус применён (или уже был применён ранее —
  повторный вызов с тем же статусом безопасен, дублей не создаёт).
- `400` — недопустимый `status` или отсутствует обязательное поле.
- `401` — неверный/отсутствующий `X-Onec-Api-Key`.
- `404` — заказ с таким `client_order_id` не найден.
- `409` — заказ уже отменён на стороне AMC (`cancelled`) — терминальный
  статус, 1С не может перевести такой заказ в `delivered`. Повторять не
  нужно, это не временная ошибка.

Рекомендация по ретраям: при `5xx` или отсутствии ответа (таймаут/сеть) —
можно повторить запрос позже, вызов идемпотентен. При `400`/`401`/`404`/`409`
повторять бессмысленно без изменения запроса — это ошибка данных или
конфигурации, не временный сбой.

## Открытые вопросы (нужен ответ 1С-стороны или совместное решение)

1. Правила матчинга контрагента/товара по естественному ключу, когда
   `onec_guid` не передан (см. ручку №1) — 1С-сторона определяет и
   документирует.
2. Нужно ли AMC уведомлять 1С при отмене заказа клиентом/менеджером
   (обратного направления, отдельная ручка) — не решено, вне объёма текущей
   работы.
3. Реальный базовый URL и порт HTTP-service 1С (`/hs/amc-integration/...`)
   — сверяется по факту публикации, как и OData-путь у синка товаров.
